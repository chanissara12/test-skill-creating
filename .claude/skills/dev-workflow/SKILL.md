# Dev Workflow

Follow these phases in order. Hard rules at the bottom apply to every phase.

## Working principles (every phase)

Goal: finish the work **and** grow the user's understanding and skills.

- Read the real code before stating a cause.
- Separate **facts**, **assumptions**, and **unknowns** in what you say.
- Show a plan before acting when the work is new, risky, or touches several parts.
- Change only the agreed scope. If you find a new approach that changes the design or widens the scope, **stop and offer options first**.
- Explain the reasoning behind significant changes; not every line.
- Show real test evidence and state what was **not** tested. Never claim success from a guess.

## 0. Preflight: required skills

Before phase 1, check that every skill in the table below is available (in the skill list, or under `~/.claude/skills/`, the project's `.claude/skills/`, or the plugin cache). Do not rely on memory of what a skill says: read the installed skill.

**If a skill is missing:**
1. Tell the user which skill is missing, who it comes from, and the install command from the table.
2. Installing downloads code from GitHub, so get a clear yes in chat, then run the command. A new skill may only show up after the session restarts: say so if it does not appear.
3. If the user declines, name the phase that depends on it and continue only with phases that do not need it. Never improvise a missing skill's job and present it as if the skill had run.

## 1. Start project
Run the `setup-workspace` skill first.

## 2. Plan
Start from the `wayfinder` skill. Grill every ticket until each decision is resolved.
When **all** tickets are grilled: run `to-spec`, then `to-tickets` (in that order).

## 3. Design: design.md / design system gate

This is a **gate, not a suggestion**. It must be passed before any of the following, in any phase:
- designing a screen, layout, component, or visual style;
- building a prototype (the `prototype` skill's UI branch, or any HTML/UI mock);
- choosing colours, fonts, radii, spacing, or other design tokens;
- writing UI code (including Tailwind theme tokens or component styles).

**How to pass the gate:**
1. **Look** in the repo for a design file or folder (for example `DESIGN.md`, `design.md`, `docs/design*`, a design-system or tokens folder). Finding one is not the end: the file may live elsewhere or not be in the repo yet.
2. **Ask the user in chat**, even if the search found something and even if it found nothing: "Is there a `design.md` or a design system I must follow? If it is not in the repo, where is it?" Do not assume the answer from the search result, from the stack's defaults, or from an earlier session.
3. **Wait for the answer** before doing any design, prototype, or UI work. Do not start "a quick prototype while we wait".
4. **Record the answer** where the work can see it (the map's Notes, the spec's Further Notes, or the ticket): the file path, or "none provided".

**After the gate:**
- If a design file or system exists: read it **in full**, apply it to every prototype variant and to the implementation (declare its tokens once, for example as Tailwind theme tokens, and use them as utilities), and say in your reply which file you applied.
- If none exists: say so explicitly and continue with neutral defaults, and label any prototype as "no design system".
- If you already built a prototype or UI before the gate was passed, say so, then rebuild or restyle it against the design file once you have it. Do not leave the unstyled version as the result.

Re-check the gate at the start of phase 4 if UI work is about to begin and the gate has not been recorded yet.

## 4. Implement
Always apply the `ponytail` skill together with `implement`: invoke it through the Skill tool before writing code, not only from memory. `implement` calls `tdd` and `code-review`; use them.
After every code change, **explain it as a lesson**: what changed, why, and how the system works
(data flow, which layer talks to which). Teach; do not just list a diff. Focus on the significant changes, not every line.
UI work follows the design file recorded at the gate (phase 3).

### Report after each change

1. Problem and the cause found
2. Files changed and why
3. How the change works
4. Test results and limitations (what was not tested)
5. What the user should understand or review further

### Learning goal

Help the user explain the problem, understand the fix, verify it, and eventually do similar work alone. Do not make them depend only on your explanation: for a new concept, use a small example or a guiding question so they truly understand.

### When the skills pull in different directions

`ponytail`, `tdd` and `code-review` agree on not building what is not needed, but they can disagree on details (for example `code-review`'s "extract the duplicate / add a type" smells add code that `ponytail` would not write). Resolve it in this order, highest first:
1. The user's explicit instruction in chat.
2. The repo's documented rules (`CLAUDE.md` files, the spec, `DESIGN.md`). They win over `ponytail`: do not strip a layer or abstraction the repo requires.
3. `ponytail`: decides **what to build and how small**. Run the "does this need to exist?" question before writing any test or code.
4. `tdd`: proves it works at the **seams agreed with the user** (confirm them before writing a test). `ponytail`'s "one check" is a minimum, not a cap: one test per behaviour slice is fine when the spec or `CLAUDE.md` asks for it.
5. `code-review`'s smell baseline: suggestions, not orders. If one conflicts with 1 to 3, skip it and say why in the review report.

### Review before finishing a ticket

Run the reviews in this order, and re-run the tests after any change they cause:
1. **`ponytail-review`** first (part of the `ponytail` plugin; cheap, reads the diff only). It finds what to cut. Cut, then re-test. It does **not** look for bugs.
2. **`code-review`** second (two axes, Standards and Spec, in parallel sub-agents). It finds bugs, missing requirements, and standards breaches, and sees the final scope because the excess is already gone.

For tickets with no behaviour to compare against a spec (project skeleton, schema scripts), `ponytail-review` alone is enough. For tickets with business logic, run both. Report the findings to the user and fix only what they approve.

## 5. Database — database-first only
- The **user** creates the database. Never create it yourself.
- You may generate SQL/migration **scripts** for the user to review and run.
- **Never execute** DB scripts, migrations, or DDL/DML yourself. Hand over the script and stop.
- Code is written against the existing schema, not the other way round.

## Hard rules
- **Never commit automatically.** No `git commit` or `git push` unless the user explicitly asks in that message.
- Never run database-modifying commands (see §5).
- **Never start design, prototype, or UI work before the design gate (§3) has been answered by the user.**
- Never skip the preflight (§0) or silently work around a missing skill.
